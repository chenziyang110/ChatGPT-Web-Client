# Dot 工作完成与队列推进验证

日期：2026-09-30；本机修复版本：1.4.22。

## 问题与实际状态

v1.4.21 的 Dot 适配等待新的稳定回复及消息操作按钮。真实测试确认，Dot 可以先确认收到，甚至先发出查询结果，后台 Agent 仍在工作。这两个消息都具有 `reply` 操作，不能单独作为完成依据。

在用户授权的已登录账号中，以同一账号会话的独立隐藏视图进行公开资料查询，没有修改用户文件、账号设置、现有任务或发送外部消息。观察到：

- 当前 Dot 摘要的 `[data-slot="thread-summary-panel-item-leading"] [data-codex-pet-state]` 从 `idle` 变为 `running`，结束时恢复 `idle`。
- `group/aeon-status` 控件的 `aria-describedby` 指向状态描述。工作时是“活跃”，停止后过一段时间才更新为 `Active 1分钟前`；控件的 Pause 标签始终存在。
- `.typing-indicator[data-visible]` 与 `.typing-bubble[data-active]` 表示新的消息活动，独立于已结束的回复。

因此当前 Dot 摘要的显式头像状态优先于状态文字。其他会话或侧栏的头像不参与判断，Pause 按钮本身不代表运行。头像未渲染时使用状态描述；未识别的状态继续观察，不能把“已收到”当成完成。

## 行为

发送前等待 Dot 当前工作空闲。发送后等待新回复和工作空闲均稳定，再推进下一条。实际任务失败并停止工作时，沿用原有错误结束规则继续后续队列；后台还在工作时不提前结束。当前工作状态每次直接从原会话页面读取，重启恢复原回执后也执行相同判断，不依赖重启前的内存变量，不重放已提交的消息。

诊断接口公开 `dotWork: working | idle | unknown`，供界面和本地 API 使用。面板显示“Dot 正在工作”“等待 Dot 工作结束”或“等待 Dot 工作状态恢复”。聊天与 Work 的判断保持原行为。

## 真实查询与 FIFO 验证

使用项目适配器串行执行两条无副作用的验收提示词。第一条要求先确认收到，再查询两项 Electron 官方说明；第二条只返回测试标记。

- 第一条约 13 秒出现带回复操作的确认消息，后台仍为 `running`。
- 约 34 秒已经出现最终结果，后台依然运行；没有发送第二条。
- 约 52 秒恢复 `idle`，稳定后约 58 秒完成本地观察。
- 第二条发送意图在第一条完成之后，获得其独立标记回复。两条各记录一次发送意图，无重发、无人工核对。
- Dot 会替换用户消息标识，因此部分结果仍为 `responseUnavailable`：只报告队列已推进，不声称保持了严格的答案关联。验收另行检查了实际最后回复的测试标记。

上述时间为一次真实查询的观察结果，不是硬编码延时，也不保证未来所有网页结构或后台任务形式均相同。当前判断按整个 Dot 频道的工作状态串行等待，没有猜测某条确认消息的自然语言是否承诺后续工作。
